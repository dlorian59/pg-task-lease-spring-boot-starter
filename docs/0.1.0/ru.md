# 0.1.0 — Фоновые отчёты в существующем Spring-приложении

[Версии](../index.md) · [English](en.md) · [Русский](ru.md) · [README](../../README.md)

Запрос отчёта должен быстро возвращать ответ, а задача — переживать перезапуск процесса. Стартер позволяет отправить задачу и написать один бизнес-метод. Начните с [полного подключения: зависимости, YAML, контроллер и сервис](../../README.md). Здесь разобраны решения приложения и адаптация рабочего примера.

## Когда подходит стартер

Он подходит Spring-приложению с PostgreSQL, которому нужны ограниченные фоновые работы: отчёты, экспорты или уведомления. Отдельный брокер не требуется. Среда — Java 17+ и Boot 4.1.2; HTTP-пример использует WebFlux. В приложении без HTTP можно убрать WebFlux и контроллер. Очередь всё равно использует R2DBC ConnectionFactory, даже если бизнес-обработчик работает через JDBC. Одного JDBC DataSource недостаточно.

Стартер не переносит произвольный вызов аннотированного метода в очередь. Производитель явно отправляет задачу; позже worker вызывает зарегистрированный метод. База API работает на Java 17, 21 и 25 LTS; дополнительная Java 27 не требует другого API или preview. Подготовка локальных артефактов и исполняемая проверка вынесены в [документ разработки](../../CONTRIBUTING.md).

<a id="http-to-file-walkthrough"></a>
## От HTTP-запроса к файлу

[Полный потребитель](../../examples/report-worker) содержит Maven- и Gradle-сборки. Копируйте классы под пакет сканирования существующего приложения: второй main-класс вашему сервису не нужен.

1. Один раз примените [schema.sql](../../examples/report-worker/schema.sql) через свой инструмент миграций. Настройте R2DBC URL и учётные данные с SELECT/INSERT/UPDATE на public.pg_task_lease. Оставьте автоматическую инициализацию схемы выключенной.
2. Добавьте [application.yml](../../examples/report-worker/src/main/resources/application.yml). Кроме подключения достаточно worker.enabled: defaults уже задают опрос, параллельность, heartbeat, повтор и тайм-ауты.
3. Добавьте [ReportService](../../examples/report-worker/src/main/java/example/ReportService.java) и [ReportController](../../examples/report-worker/src/main/java/example/ReportController.java). PUT /reports/{uuid}?quarter=2026-Q4 возвращает 202 после принятия базой. Повтор UUID с тем же кварталом даёт 202 без новой строки; с другим кварталом тоже даёт 202, сохраняя исходную задачу. Некорректный квартал — 400.
4. Добавьте [ReportJobs](../../examples/report-worker/src/main/java/example/ReportJobs.java). Обработчик пишет reports/{uuid}.csv. GET /reports/{uuid} возвращает состояние: DONE означает успешный возврат обработчика и подтверждение очереди. Отсутствующая задача — 404.
5. Замените демонстрационные итоги, место хранения и проверки доступа. Локальный каталог и фиксированные данные делают результат примера проверяемым. Работникам на разных хостах нужно подходящее общее или внешнее хранилище. Если данные отчёта меняются, сохраните снимок/версию, чтобы повтор генерировал те же байты.

[ReportVerification](../../examples/report-worker/src/main/java/example/ReportVerification.java) — отдельная конечная проверка, включаемая явно. Она делает реальные HTTP-запросы отправки и дубликатов, включая дубликат с другим кварталом, ждёт DONE и проверяет точное содержимое CSV и одну попытку. Обычный сервер продолжает работать. Этот проверочный класс не нужен в исходниках вашего приложения.

Переименование атомарно на поддерживающей его файловой системе, но не обещает сохранность после отказа накопителя. После записи файла подтверждение может потеряться, что приведёт к повтору. Ключ результата по UUID предотвращает второе имя; содержимое и последующие эффекты приложение тоже должно сделать безопасными для повторов.

<a id="submission-and-duplicates"></a>
## Отправка и дубликаты

```java
queue.submit(TaskRequest.ready(id, "reports", "2026-Q4"));
```

TaskRequest.ready сохраняет UUID вызывающего кода, задаёт priority 0, maxAttempts 5 и нулевую задержку. submit возвращает true для новой строки и false для существующего UUID. Исходная строка не перезаписывается; UUID общий для всех очередей. [Сервис](../../examples/report-worker/src/main/java/example/ReportService.java) проверяет, что дубликат относится к очереди reports. Содержимое первой отправки сохраняется; сравнение бизнес-содержимого core не выполняет.

Сохраните UUID до первой попытки. Если ответ потерялся, повторите с теми же UUID и содержимым. Новый случайный UUID на каждый сетевой повтор создаёт новую задачу. Очистка строк удаляет историю дедупликации; храните терминальные строки как минимум в течение необходимого окна повторов. В примере проверка дубликата может вернуть 404, если строка удалена между submit и чтением.

Возвращённый из контроллера Mono подписывает WebFlux. Вызов submit без подписки ничего не делает. Не прячьте subscribe без ожидания в сервисе: он разрывает связь между принятием и HTTP-результатом. Запрос может отмениться после commit базы, поэтому HTTP-ошибка не доказывает отсутствие задачи.

<a id="task-choices"></a>
## Параметры конкретной задачи

```java
var request = TaskRequest.ready(id, "reports", quarter)
        .withPriority(10)
        .withMaxAttempts(2)
        .withDelay(Duration.ofMinutes(5));
```

Каждый метод создаёт новый проверенный запрос; исходный не меняется. Приоритет — предпочтение при захвате, а не полный порядок исполнения между worker. Большее число предпочтительнее; постоянный поток приоритетных задач может вытеснить остальные. Задержку отсчитывает PostgreSQL. maxAttempts ограничивает захваты, включая прерванные сбоем, а не успешные вызовы обработчика.

Задержка подходит для отложенного экспорта, меньший бюджет — для непереходящих ошибок. Классификация ошибок и административная новая отправка после DEAD остаются политикой приложения. Пять попыток — стартовое значение, не гарантия доступности. Задержка запроса влияет на первую доступность; worker.retry-delay — на повтор после ошибки или восстановления.

<a id="register-business-work"></a>
## Бизнес-обработчик

Для обычного блокирующего файлового/JDBC-кода используйте полный [CSV-обработчик](../../examples/report-worker/src/main/java/example/ReportJobs.java):

```java
@PgTaskHandler(value = "reports", blocking = true)
public void generate(TaskLease lease) throws IOException
```

Это фрагмент объявления: тело и импорты находятся в исходнике по ссылке. Стартер оборачивает вызов в cold publisher и выполняет на общем boundedElastic. Регистрация не вызывает метод. Worker ждёт нормального возврата перед подтверждением, считает исключение ошибкой попытки и независимо продлевает аренду. При перегрузке общего scheduler ожидание тоже расходует handler-timeout: ограничивайте параллельность и ресурсы зависимостей. Стартер не владеет общим scheduler Reactor и не закрывает его.

Отмена запрашивает прерывание; Java-код, файловый или сетевой вызов могут его игнорировать. Такая работа может закончиться после остановки или потери аренды. Прерывание не является откатом: настраивайте тайм-ауты и идемпотентность зависимостей. concurrency ограничивает подписанные попытки, но не произвольно долго продолжающуюся внешнюю работу, которая не реагирует на отмену.

Для реактивного бизнес-кода сохраняется основной контракт:

```java
@PgTaskHandler("reports")
public Mono<Void> generate(TaskLease lease) {
    return reports.generateIdempotently(lease.id(), lease.payload());
}
```

Здесь reports — реактивный сервис приложения. Возвращайте completion после завершения эффекта; не блокируйте поток при сборке publisher. Стартер не меняет scheduler реактивного обработчика. Для программной регистрации остаётся bean TaskHandlerRegistration("reports", lease -> ...); для каждой очереди выбирайте либо его, либо аннотацию.

Метод должен быть public, нестатическим и нефинальным на eager singleton bean. blocking=true требует void, основной режим — Mono<Void>; оба принимают один TaskLease. Обнаружение происходит при старте worker после создания прокси. Вызов сохраняет настроенный Spring advice. JDBC @Transactional void-метод может завершить бизнес-транзакцию до подтверждения; реактивному нужен соответствующий transaction manager. Ни один режим не объединяет доменные изменения и очередь в одну транзакцию. Прямой/self-вызов не получает аренду. [Ограничения прокси и альтернативы](reference.ru.md).

<a id="operational-contract-and-settings"></a>
## Контракт и настройки

Все настройки работника имеют префикс pg-task-lease.worker.

| Настройка | По умолчанию | Значение |
|---|---|---|
| enabled | false | Явно включает управляемую обработку. |
| concurrency | 4 | Общий предел активной партии для всех зарегистрированных очередей: 1–1000. |
| owner | spring-worker | Диагностическое имя; владение проверяется токеном и поколением. |
| poll-interval | 1s | Пауза после завершения предыдущей партии, включая ошибку. |
| lease-time | 30s | Срок владения по часам PostgreSQL. |
| heartbeat-interval | 10s | Пауза между завершёнными вызовами heartbeat активной задачи. |
| recovery-interval | 10s | Пауза после прохода восстановления по зарегистрированным очередям. |
| recovery-batch-size | 100 | Не более 1–1000 просроченных строк на очередь за проход. |
| retry-delay | 5s | Задержка после ошибки обработчика или восстановления аренды. |
| operation-timeout | 5s | Ограничение каждой операции очереди от подписки, включая ожидание пула. |
| handler-timeout | 5m | Максимальная длительность одной попытки обработчика. |

Длительности задаются целыми миллисекундами, положительны (retry-delay допускает ноль) и не превышают 365 дней. Сумма heartbeat-interval + operation-timeout должна быть меньше lease-time. Некорректные значения и повторная регистрация одной очереди останавливают запуск. Включённому worker нужен хотя бы один аннотированный метод или явная регистрация. pg-task-lease.enabled=false отключает всю автоконфигурацию стартера.

Одновременно выполняется одна партия; очереди обходятся по кругу. До следующего опроса worker ждёт завершения всей партии. Медленная задача может задержать другие очереди, но независимые heartbeat и восстановление продолжаются. Нет неограниченной очереди тиков или локального запаса аренд, ожидающих свободный слот. Настраивайте пул с запасом для обработки, heartbeat и восстановления.

После успешного обработчика вызывается complete. Ошибка или тайм-аут обработчика вызывает fail с диагностикой, содержащей только класс исключения; maxAttempts задачи ограничивает число захватов. Ошибка или false от heartbeat отменяет publisher обработчика. Ошибка или false от подтверждения не превращает успешно выполненный обработчик в новую бизнес-ошибку; неоднозначный результат базы остаётся для диагностики и восстановления.

Остановка контекста отменяет подписки работника; перед новым подтверждением проверяется текущая сессия. Уже отправленная операция базы всё ещё может зафиксироваться. Остановка не ждёт некорректно отменяемую внешнюю работу, не откатывает её эффект и не завершает блокирующий Java-код принудительно. Неподтверждённые аренды остаются для восстановления по истечении срока. Обработчики должны поддерживать реактивную отмену и выносить блокирующую работу из event loop и таймеров.

At-least-once попытки зависят от сохранённых строк, работающих обработчиков/восстановления и долговечности PostgreSQL. Проверка аренды защищает строки очереди, но не внешний API автоматически. Используйте ключ идемпотентности или транзакционную дедупликацию на стороне эффекта. Если отправка задачи должна быть атомарна с доменными изменениями, нужен outbox или явная транзакционная схема. Хранение DONE/DEAD остаётся политикой приложения.

## Диагностика и проверки

- Артефакт не найден: установите core 0.3.0 и starter 0.1.0 в тот Maven Local, который использует потребитель.
- Нет таблицы: примените миграцию в базу из spring.r2dbc.url; стартер её не создаёт.
- Задачи не обрабатываются: проверьте worker.enabled, имя очереди обработчика, READY/задержку и бюджет попыток.
- Несколько ConnectionFactory: оставьте одного кандидата или отметьте нужный bean @Primary.
- Повторяются предупреждения task/claim: проверьте доступность базы, тайм-ауты, ёмкость пула и длительность обработчика. Payload и сообщения исключений намеренно не выводятся работником в лог.
- Задача DEAD: изучите attempts и lastError, устраните бизнес-причину и осознанно создайте новую задачу по своей политике повторов.

## Что нужно знать

Постоянный ID предотвращает повторную отправку, пока строка существует. Действующая аренда разрешает переходы очереди, но не авторизует и не дедуплицирует другую систему. Worker владеет опросом и отменой, приложение — бизнес-данными, миграциями, доступом и идемпотентностью результата. Defaults сокращают настройку; меняйте их по реальным бюджетам обработчика и зависимостей.

[Планировщики Reactor](https://projectreactor.io/docs/core/release/reference/coreFeatures/schedulers.html) описывают boundedElastic и выполнение подписки. [Конфигурация R2DBC в Boot](https://docs.spring.io/spring-boot/reference/data/sql.html#data.sql.r2dbc) определяет используемое здесь подключение ConnectionFactory.
