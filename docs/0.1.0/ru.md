# 0.1.0 — фоновые отчёты в Spring Boot

[Версии](../index.md) · [English](en.md) · [Русский](ru.md) · [README](../../README.md)

## Задача и назначение стартера

Подготовка отчёта может пережить HTTP-запрос или процесс, принявший запрос. Сохраните задачу с постоянным UUID, передайте её работнику и формируйте идемпотентный результат. Базовая библиотека отвечает за владение задачей в PostgreSQL. Стартер добавляет конфигурацию Spring и жизненный цикл приложения: опрос, ограниченные партии, heartbeat, восстановление, тайм-аут обработчика и подтверждение с проверкой аренды.

Приложение задаёт подключение к PostgreSQL и явные методы @PgTaskHandler существующих singleton beans либо beans TaskHandlerRegistration. Сканирования classpath и скрытого сериализатора бизнес-данных нет. Если Boot предоставляет однозначный ConnectionFactory, стартер создаёт PgTaskQueue; фоновая обработка включается отдельной настройкой. Собственные PgTaskQueue и PgTaskWorker имеют приоритет.

## Локальная установка

Нужны JDK 17+, Maven 3.8+ и две рабочие копии рядом. Используются Spring Boot 4.1.2 и базовая библиотека pg-task-lease 0.3.0.

```bash
cd pg-task-lease
./gradlew publishToMavenLocal
cd ../pg-task-lease-spring-boot-starter
./gradlew build publishToMavenLocal
```

Зависимости для Boot-приложения:

```xml
<dependency>
  <groupId>io.github.59alex</groupId>
  <artifactId>pg-task-lease-spring-boot-starter</artifactId>
  <version>0.1.0</version>
</dependency>
<dependency>
  <groupId>org.postgresql</groupId>
  <artifactId>r2dbc-postgresql</artifactId>
  <scope>runtime</scope>
</dependency>
```

Версию драйвера выбирает BOM Spring Boot. Это установка через Maven Local; публикация в реестре не заявляется.

## Подготовка базы и включение работника

До включения worker примените [schema.sql](../../examples/report-worker/schema.sql) один раз через инструмент миграций. Скрипт создаёт таблицу очереди и индексы. Стартер не выполняет DDL, не удаляет таблицы и не инициализирует базу автоматически. Рабочей роли нужны SELECT, INSERT и UPDATE на public.pg_task_lease. Имена очередей разделяют выбор задач, но не права в PostgreSQL.

```properties
spring.r2dbc.url=${TASKS_R2DBC_URL}
spring.r2dbc.username=${TASKS_DB_USER}
spring.r2dbc.password=${TASKS_DB_PASSWORD}
spring.r2dbc.pool.max-size=8
spring.r2dbc.pool.initial-size=0
spring.sql.init.mode=never
pg-task-lease.worker.enabled=true
pg-task-lease.worker.concurrency=2
```

## Регистрация бизнес-обработчика

Добавьте @PgTaskHandler("reports") к публичному методу Mono<Void> method(TaskLease) обычного singleton bean, создаваемого при запуске Spring:

```java
@PgTaskHandler("reports")
public Mono<Void> generate(TaskLease lease) {
    return reports.generateIdempotently(lease.id(), lease.payload());
}
```

reports здесь — реактивный сервис вашего приложения. Полный исполняемый обработчик находится в [ReportJobs.java](../../examples/report-worker/src/main/java/example/ReportJobs.java), его запускает [ReportApplication.java](../../examples/report-worker/src/main/java/example/ReportApplication.java): она пишет детерминированный CSV в файл по UUID задачи через временный файл и атомарное переименование, а файловые операции выполняет на boundedElastic. Повтор заменяет тот же отчёт, а не создаёт дополнительный результат. Демонстрационные итоги явно обозначены в коде; замените их чтением своих данных.

Аннотация регистрирует обработчик: она не является аспектом и не отправляет прямые вызовы в очередь. Метод вызывается на конечном bean/proxy Spring, сохраняя настроенные @Transactional/@Around. Для реактивной транзакции нужен реактивный transaction manager. Завершение транзакции обработчика и подтверждение очереди остаются отдельными операциями.

Метод должен быть public, нестатическим, нефинальным, принимать один TaskLease и возвращать Mono<Void>. JDK-прокси должен предоставлять этот метод через интерфейс; class proxy требует допускающий наследование класс. Lazy/prototype обработчики и продукты FactoryBean автоматически не обнаруживаются; scoped/dynamic proxy targets отклоняются. При старте worker фиксируются уже созданные singleton beans текущего контекста. Прямой/self-вызов не получает аренду, а self-invocation обходит AOP-прокси Spring. См. [полный справочник и альтернативы](reference.ru.md).

Для ручной регистрации остаётся прежняя форма bean; не аннотируйте одновременно обработчик той же очереди:

```java
@Bean
TaskHandlerRegistration reportHandler(ReportService reports) {
    return new TaskHandlerRegistration("reports", lease ->
        reports.generateIdempotently(lease.id(), lease.payload()));
}
```

Отправка через внедрённый PgTaskQueue:

```java
Mono<Boolean> accepted = queue.submit(new TaskRequest(
    stableRequestId, "reports", "2026-Q4", 0, 3, Duration.ZERO));
```

Сохраняйте stableRequestId в процессе производителя и повторяйте отправку с ним же. Подписывайтесь через жизненный цикл запроса или приложения. Новый ID при каждой сетевой попытке создаёт отдельные задачи. В примере ApplicationRunner один раз отправляет задачу, а затем на границе консольной программы ждёт DONE и проверяет содержимое файла.

## Запуск настоящего примера

После локальной установки выше, при доступном Docker:

```bash
cd examples/report-worker
./run-demo.sh
```

Скрипт создаёт отдельную PostgreSQL на случайном порту localhost, явно применяет миграцию, собирает Boot-приложение через Maven Local, запускает его и останавливает только свой контейнер при выходе. Демонстрационные учётные данные относятся только к этой временной базе.

Последняя строка приложения:

```text
REPORT_DONE task=<uuid> attempts=1 path=reports/<uuid>.csv
```

Содержимое файла:

```csv
quarter,invoices,total
2026-Q4,3,450.00
```

Перед выходом приложение проверяет сохранённое состояние DONE и точное содержимое CSV. Пример конечный; в серверном приложении контекст Spring остаётся открытым и тот же worker продолжает работу. Если Docker недоступен, подготовьте отдельную PostgreSQL самостоятельно, примените schema.sql, задайте TASKS_R2DBC_URL, TASKS_DB_USER и TASKS_DB_PASSWORD, затем выполните `mvn package` и `java -jar target/report-worker-0.1.0.jar` в каталоге примера.

## Контракт и настройки

Все настройки работника имеют префикс pg-task-lease.worker.

| Настройка | По умолчанию | Значение |
|---|---|---|
| enabled | false | Явно включает управляемую обработку. |
| concurrency | 4 | Общий предел активной партии для всех зарегистрированных очередей: 1–1000. |
| owner | spring-worker | Диагностическое имя; владение проверяется токеном и поколением. |
| poll-interval | 1s | Пауза после завершения предыдущей партии, включая ошибку. |
| lease-time | 30s | Срок владения по часам PostgreSQL. |
| heartbeat-interval | 10s | Пауза между завершёнными вызовами heartbeat активной задачи. |
| recovery-interval | 10s | Пауза после прохода восстановления по зарегистрированным очередям. |
| recovery-batch-size | 100 | Не более 1–1000 просроченных строк на очередь за проход. |
| retry-delay | 5s | Задержка после ошибки обработчика или восстановления аренды. |
| operation-timeout | 5s | Ограничение каждой операции очереди от подписки, включая ожидание пула. |
| handler-timeout | 5m | Максимальная длительность одной попытки обработчика. |

Длительности задаются целыми миллисекундами, положительны (retry-delay допускает ноль) и не превышают 365 дней. Сумма heartbeat-interval + operation-timeout должна быть меньше lease-time. Некорректные значения и повторная регистрация одной очереди останавливают запуск. Включённому worker нужен хотя бы один аннотированный метод или явная регистрация. pg-task-lease.enabled=false отключает всю автоконфигурацию стартера.

Одновременно выполняется одна партия; очереди обходятся по кругу. До следующего опроса worker ждёт завершения всей партии. Медленная задача может задержать другие очереди, но независимые heartbeat и восстановление продолжаются. Нет неограниченной очереди тиков или локального запаса аренд, ожидающих свободный слот. Настраивайте пул с запасом для обработки, heartbeat и восстановления.

После успешного обработчика вызывается complete. Ошибка или тайм-аут обработчика вызывает fail с диагностикой, содержащей только класс исключения; maxAttempts задачи ограничивает число захватов. Ошибка или false от heartbeat отменяет publisher обработчика. Ошибка или false от подтверждения не превращает успешно выполненный обработчик в новую бизнес-ошибку; неоднозначный результат базы остаётся для диагностики и восстановления.

Остановка контекста отменяет подписки работника; перед новым подтверждением проверяется текущая сессия. Уже отправленная операция базы всё ещё может зафиксироваться. Остановка не ждёт некорректно отменяемую внешнюю работу, не откатывает её эффект и не завершает блокирующий Java-код принудительно. Неподтверждённые аренды остаются для восстановления по истечении срока. Обработчики должны поддерживать реактивную отмену и выносить блокирующую работу из event loop и таймеров.

At-least-once попытки зависят от сохранённых строк, работающих обработчиков/восстановления и долговечности PostgreSQL. Проверка аренды защищает строки очереди, но не внешний API автоматически. Используйте ключ идемпотентности или транзакционную дедупликацию на стороне эффекта. Если отправка задачи должна быть атомарна с доменными изменениями, нужен outbox или явная транзакционная схема. Хранение DONE/DEAD остаётся политикой приложения.

## Диагностика и проверки

- Артефакт не найден: установите core 0.3.0 и starter 0.1.0 в тот Maven Local, который использует потребитель.
- Нет таблицы: примените миграцию в базу из spring.r2dbc.url; стартер её не создаёт.
- Задачи не обрабатываются: проверьте worker.enabled, имя очереди обработчика, READY/задержку и бюджет попыток.
- Несколько ConnectionFactory: оставьте одного кандидата или отметьте нужный bean @Primary.
- Повторяются предупреждения task/claim: проверьте доступность базы, тайм-ауты, ёмкость пула и длительность обработчика. Payload и сообщения исключений намеренно не выводятся работником в лог.
- Задача DEAD: изучите attempts и lastError, устраните бизнес-причину и осознанно создайте новую задачу по своей политике повторов.
